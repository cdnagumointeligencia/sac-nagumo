CAPÍTULO 6
Arquitetura Recomendada da Solução

Este capítulo consolida todas as recomendações apresentadas anteriormente em uma arquitetura única, definindo a organização dos módulos, o fluxo de dados, os padrões de desenvolvimento e a estrutura recomendada para o Firestore. O objetivo é estabelecer uma base arquitetural que permita crescimento, manutenção simplificada e alta confiabilidade operacional.

6.1 Objetivo

Após a implementação das correções apresentadas nos capítulos anteriores, o Sistema SAC Nagumo deixará de ser um conjunto de módulos independentes sincronizados por estruturas completas de dados e passará a operar segundo uma arquitetura orientada a documentos, eventos e sincronização incremental.

Este capítulo descreve como essa arquitetura deverá ser organizada.

6.3 Camada de Interface

A interface deverá ser responsável exclusivamente pela interação com o usuário.

Ela não deverá:

acessar diretamente o Firestore;
conhecer a estrutura das coleções;
executar regras de negócio;
realizar validações complexas.

Sua função será:

exibir informações;
capturar entradas do usuário;
apresentar mensagens;
encaminhar comandos para a camada de negócio.
Exemplo

Hoje:

Botão

↓

Firestore

Arquitetura proposta:

Botão

↓

Controller

↓

Serviço

↓

Persistência

↓

Firestore
Benefícios

✔ Interface mais simples.

✔ Código reutilizável.

✔ Facilidade de manutenção.

6.4 Camada de Negócio

Toda regra operacional deverá permanecer nesta camada.

Exemplos:

validação de chamados;
geração automática de notas;
cálculo de produtividade;
regras de usuários;
permissões;
filtros.

Nenhuma regra deverá existir na interface.

Exemplo
Tela

↓

Cadastrar Chamado

↓

Validação

↓

Persistência
Benefícios

Caso futuramente exista:

aplicativo Android;
aplicativo iOS;
API REST;
integração ERP;

todas utilizarão exatamente as mesmas regras.

6.5 Camada de Persistência

Esta camada será responsável por toda comunicação com o Firestore.

Ela deverá encapsular operações como:

Criar Documento

Editar Documento

Excluir Documento

Consultar Documento

Consultar Coleção

Nenhum outro módulo deverá chamar diretamente:

set()

update()

delete()

onSnapshot()

Essas operações deverão existir apenas nesta camada.

Benefícios

✔ Facilidade para manutenção.

✔ Menor duplicação de código.

✔ Melhor tratamento de erros.

✔ Centralização da sincronização.

6.16 Resultado Esperado

Ao final da reorganização arquitetural, o sistema apresentará:

Item	Arquitetura Atual	Arquitetura Recomendada
Comunicação com banco	Distribuída entre módulos	Centralizada em uma camada de persistência
Organização do projeto	Funcional por arquivos	Modular por responsabilidade
Estrutura Firestore	Mistura documentos e conjuntos	Documento por entidade
Tratamento de erros	Localizado	Padronizado
Organização dos objetos	Variável entre módulos	Modelo único com metadados
Fluxo de dados	Direto entre interface e banco	Em camadas (UI → Controller → Service → Repository → Firestore)
Conclusão do Capítulo 6

Com a arquitetura proposta neste capítulo, o Sistema SAC Nagumo passa a adotar uma organização moderna, modular e escalável. A separação de responsabilidades reduz o acoplamento entre os módulos, facilita a manutenção e prepara o sistema para futuras integrações, como aplicativos móveis, APIs ou novos módulos operacionais.

Além disso, a adoção de uma camada única de persistência e de um modelo consistente de documentos garante maior previsibilidade na sincronização e reduz significativamente a complexidade da evolução do software.
