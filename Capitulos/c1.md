CAPÍTULO 1
Introdução
1.1 Objetivo

Este documento apresenta o plano técnico de evolução do Sistema SAC Nagumo com base na análise dos riscos identificados na arquitetura atual.

Diferentemente do relatório de diagnóstico, cujo objetivo foi identificar vulnerabilidades e potenciais problemas operacionais, este documento estabelece um conjunto de recomendações técnicas destinadas à correção definitiva das causas identificadas, propondo alterações estruturais que permitam elevar o nível de confiabilidade do sistema sem comprometer sua simplicidade de utilização.

O documento deverá servir como referência para futuras manutenções, evoluções e refatorações da aplicação.

As recomendações aqui descritas abrangem os seguintes módulos do sistema:

1.3 Objetivos Técnicos

A implementação das recomendações apresentadas neste documento possui os seguintes objetivos principais:

Eliminar riscos de perda de dados

Garantir que alterações realizadas por diferentes usuários não provoquem exclusões ou sobrescritas acidentais.

Melhorar a integridade das informações

Cada registro deverá possuir identidade própria e ciclo de vida independente, permitindo operações seguras de criação, edição e exclusão.

Melhorar a concorrência

O sistema deverá suportar múltiplos operadores trabalhando simultaneamente sobre a mesma base de dados sem provocar inconsistências.

Preparar o sistema para crescimento

A arquitetura deverá suportar aumento contínuo da quantidade de registros sem necessidade de alterações estruturais.

Melhorar a rastreabilidade

Todas as operações críticas deverão possuir mecanismos que permitam identificar:

quem alterou;
quando alterou;
qual informação foi modificada.
Melhorar a experiência do usuário

O operador deverá receber informações claras sobre:

sincronização;
falhas;
conflitos;
sucesso das gravações.
1.4 Situação Atual

A análise técnica identificou que a aplicação possui uma arquitetura funcional e relativamente simples, porém fortemente baseada em estruturas completas de dados mantidas em memória do navegador.

Grande parte das alterações realizadas pelo usuário provoca a gravação integral de conjuntos de registros em vez da atualização apenas dos elementos modificados.

Embora essa estratégia simplifique o desenvolvimento inicial, ela apresenta limitações quando utilizada em ambientes compartilhados por diversos operadores.

Entre as principais características observadas estão:

armazenamento híbrido utilizando localStorage e Firestore;
sincronização baseada em substituição completa de coleções ou documentos;
ausência de controle de concorrência;
ausência de versionamento;
ausência de confirmação efetiva de sincronização;
utilização de documentos contendo grandes estruturas de dados.

Essas características tornam o sistema funcional em ambientes com poucos usuários simultâneos, porém aumentam significativamente o risco de inconsistências à medida que o uso cresce.

1.5 Princípios da Evolução Proposta

Todas as alterações sugeridas neste documento seguem os seguintes princípios arquiteturais.

1.5.1 Operações Incrementais

Sempre que possível, apenas o registro alterado deverá ser enviado ao banco de dados.

Não deverão existir rotinas responsáveis por apagar integralmente coleções para recriá-las posteriormente.

1.5.2 Documentos Independentes

Cada entidade do sistema deverá possuir seu próprio documento.

Exemplo:

Chamado
↓

Documento independente

Senha SAC
↓

Documento independente

Nota

↓

Documento independente

Mercadoria

↓

Documento independente

Essa abordagem reduz drasticamente o risco de conflitos entre usuários.

1.5.3 Identificadores Permanentes

Todo registro deverá possuir um identificador único e permanente.

Esse identificador nunca deverá depender de informações que possam mudar durante a vida útil do registro, como:

nome;
data;
mês;
número sequencial temporário.

A recomendação é utilizar identificadores automáticos gerados pelo Firestore (Auto ID) ou UUIDs, mantendo os campos de negócio (como número do chamado ou data) apenas como atributos pesquisáveis.

1.5.4 Sincronização em Tempo Real

Sempre que possível, a sincronização entre clientes deverá utilizar mecanismos de atualização incremental.

Alterações realizadas por um operador deverão refletir automaticamente para os demais usuários sem necessidade de reconstrução completa das tabelas.

1.5.5 Tolerância a Falhas

Falhas temporárias de rede não deverão resultar em perda silenciosa de informações.

O sistema deverá ser capaz de:

detectar falhas;
informar o usuário;
tentar novamente a sincronização;
manter a operação consistente.
1.5.6 Escalabilidade

As decisões arquiteturais deverão considerar crescimento contínuo da base de dados.

O desempenho esperado para uma coleção contendo 100 registros deverá permanecer aceitável mesmo quando essa coleção atingir milhares de documentos.

1.6 Arquitetura Atual (Visão Simplificada)

De forma resumida, o fluxo atual pode ser representado pelo seguinte diagrama:

             Usuário

                │

                ▼

      Interface HTML

                │

                ▼

      Objetos em Memória

                │

      localStorage

                │

       Firestore


Em diversos pontos da aplicação, o envio ao Firestore ocorre através da gravação integral de estruturas mantidas em memória.

Essa estratégia simplifica a implementação, porém amplia a possibilidade de conflitos quando diferentes clientes operam simultaneamente sobre os mesmos conjuntos de dados.

1.7 Arquitetura Recomendada

A evolução proposta altera o modelo para operações independentes por documento.

                 Usuário

                    │

                    ▼

             Interface HTML

                    │

                    ▼

          Registro Alterado

                    │

          Apenas este registro

                    │

                    ▼

            Firestore

                    │

            onSnapshot()

                    │

        Atualização Incremental

                    │

                    ▼

         Demais Usuários

Nesse modelo:

apenas o registro alterado é sincronizado;
alterações concorrentes tornam-se independentes;
o volume de dados transmitido é reduzido;
elimina-se a necessidade de substituir coleções inteiras.
1.8 Estratégia Geral de Implementação

Para minimizar riscos durante a evolução do sistema, recomenda-se que as alterações sejam executadas em fases independentes.

A sequência sugerida é:

Fase 1 – Correções Críticas

eliminação das rotinas de substituição completa de coleções;
individualização dos documentos;
revisão dos identificadores.

Fase 2 – Concorrência

sincronização incremental;
controle de conflitos;
atualização em tempo real.

Fase 3 – Estrutura

reorganização das coleções;
melhorias no backup;
separação por ano e mês.

Fase 4 – Segurança

autenticação;
regras do Firestore;
remoção de credenciais expostas.

Fase 5 – Otimizações

desempenho;
monitoramento;
logs;
auditoria.
