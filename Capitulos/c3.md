Sistema SAC Nagumo
CAPÍTULO 3
Correções de Concorrência e Sincronização Multiusuário

Este capítulo apresenta as soluções para os problemas classificados como ALTO no relatório de riscos (itens 6 a 11), relacionados à concorrência entre usuários, sincronização em tempo real e integridade dos dados em ambientes com múltiplos operadores. As recomendações desta seção assumem como base a nova arquitetura proposta no Capítulo 2.

3.1 Objetivos

Após a implementação das correções críticas descritas anteriormente, o próximo passo consiste em tornar o sistema verdadeiramente preparado para operação simultânea.

Os objetivos deste capítulo são:

permitir múltiplos operadores utilizando o sistema ao mesmo tempo;
impedir que uma edição destrua outra;
evitar perda de digitação;
detectar conflitos automaticamente;
garantir consistência entre navegadores.
3.2 Situação Atual

Na arquitetura atual, cada navegador mantém sua própria cópia dos dados em memória.

Sempre que ocorre uma alteração, a interface frequentemente reconstrói tabelas inteiras, e os dados são sincronizados utilizando o estado local do navegador.

Esse modelo funciona adequadamente quando apenas um usuário utiliza o sistema.

Entretanto, quando dois ou mais operadores trabalham simultaneamente, surgem diversos cenários de conflito.

3.3 Correção Nº 6
Atualização Incremental da Interface
Situação Atual

O relatório identifica que determinadas alterações provocam reconstrução completa da tabela.

Fluxo simplificado:

Recebe alteração

↓

tbody.innerHTML = ""

↓

Reconstrói toda tabela

Embora simples, essa abordagem apresenta efeitos colaterais importantes:

perda do foco do cursor;
perda de digitação;
perda de seleção;
piscar da interface;
baixo desempenho.
Objetivo

Atualizar somente a linha modificada.

Jamais reconstruir toda a tabela quando apenas um registro sofreu alteração.

Estratégia Recomendada

Cada registro deverá possuir um identificador permanente.

Exemplo:

TR

data-id="A8129"

Quando chegar uma atualização:

↓

↓

Atualiza células

↓

Fim

Nenhuma outra linha deverá sofrer alteração.

Utilização do Firestore

A sincronização deverá utilizar listeners em tempo real.

Fluxo:

↓

↓

Atualizar somente este documento

↓

Atualizar somente esta linha
Benefícios

3.4 Correção Nº 7
Isolamento da Fila de Sincronização
Situação Atual

O relatório aponta que o debounce de gravação utiliza chaves genéricas, o que pode gerar fragilidade caso a aplicação evolua para permitir mudança de CD sem recarregar a página.

Embora o risco atual seja reduzido, recomenda-se adequar a arquitetura desde já.

Objetivo

Cada contexto operacional deverá possuir sua própria fila de sincronização.

Estrutura Recomendada

Em vez de:

Timer

↓

Senha SAC

Utilizar:

Timer

↓

Senha SAC

↓

CD1

Outro:

Timer

↓

Senha SAC

↓

CD2

Outro:

Timer

↓

Notas

↓

CD3

Cada módulo trabalha isoladamente.

Benefícios

Evita cruzamento de operações.

Melhora organização interna.

Facilita manutenção futura.

Prioridade

★★★☆☆

3.5 Correção Nº 8
Controle de Conflitos de Edição
Situação Atual

Atualmente, dois usuários podem editar simultaneamente o mesmo registro.

Não existe mecanismo para detectar esse conflito.

O último salvamento simplesmente substitui o anterior.

Objetivo

Permitir que o sistema identifique alterações concorrentes.

Estratégia Recomendada

Adicionar metadados em todos os documentos.

3.10 Resultado Esperado

Após a implementação deste capítulo, o sistema passará a operar de forma muito mais consistente em ambientes com múltiplos usuários.

Os principais ganhos incluem:

detecção automática de conflitos;
prevenção de registros duplicados;
indicadores claros de sincronização;
